# Interaction benchmark corpus and results

**Owner:** tracker issue 0032. **Status:** the corpus, operation mix, metrics
and locality checks are implemented and run in `scripts/verify.sh`; the
numbers below record one measured run on one named host.

Performance is a release criterion for Domowik, not later polish
([AGENTS.md](../CLAUDE.md)). This document exists so that a performance claim
about wall editing, room detection or recomputation scope can be checked
instead of believed. Everything here is generated by `crates/domowik-bench`;
nothing was measured by hand.

## Reference environment

A number without its machine is not a measurement. Every figure below was
produced on exactly this host, and figures from any other host are not
comparable with them.

| Property | Value |
|---|---|
| Machine | Apple M4 Max |
| Cores | 16 logical |
| Memory | 48 GiB |
| Operating system | macOS 26.6.2 (`arm64`) |
| Toolchain | the channel pinned in `rust-toolchain.toml` |
| Profile | `release` — `opt-level = 3`, `lto = "fat"`, `codegen-units = 1` |
| Allocator | the system allocator, wrapped for counting |
| Date measured | 2026-09-02 |
| Samples | 200 per class, after 20 discarded warmups |
| Runs | three; the tables record the first, and the three agreed to within 17.2% on every p50 |

The machine was not otherwise idle-locked and no CPU affinity was set. That is
why the regression tripwire below is set outside the observed run-to-run
spread rather than at the recorded value.

## Reproducing it

```sh
cargo run --release -p domowik-bench -- --iterations 200 --warmup 20
```

`--smoke` runs three iterations of everything; that is the mode
`scripts/verify.sh` uses, and it proves the harness still works rather than
producing a measurement. `cargo bench -p domowik-bench` runs the same
workloads under criterion, which keeps a baseline between runs and reports
changes; the harness binary reports allocation counts and locality, which
criterion cannot express.

## What is measured

One sample times ONE gesture against freshly prepared state:

1. `Session::commit` — validation, log delivery, projection.
2. The derived-geometry rebuild for the level — occupied region (R3.2.1) and
   room faces (R5.1.1).

That pair is what an editor pays per user action. Preparation — cloning the
session and the batch — is outside the timed region; inside it, the number
would be dominated by copying the document.

**Not measured here:** rendering and frame budgets (issue 0033), container
read and write (issue 0029), asset pipeline cost (issue 0026), and hit testing
and marquee selection (issue 0012).

### Method

- **Percentiles** are nearest-rank: samples sorted ascending, the p-th
  percentile is the sample at index `ceil(p/100 × n) − 1`. No interpolation,
  no outlier rejection. Every sample taken is in the summary.
- **Allocation counts** come from a counting wrapper around the system
  allocator, armed immediately before the timed body so the figures exclude
  preparation. `peak` is the greatest live-byte total ABOVE the level already
  resident, which is what "this gesture's memory cost" means.
- **Correctness tests assert nothing about time.** Issue 0032 requires
  benchmarks and correctness tests to be separate artifacts; the locality
  checks in `crates/domowik-bench/tests/locality.rs` are pure correctness and
  hold whatever the machine is doing.

## The corpus

Generated by a fixed algorithm from fixed seeds with deterministic
identifiers, so the same build produces byte-identical corpora on any host —
`tests/corpus.rs` asserts both reproducibility and validity. Layouts are
generated from the normative rules of BEHAVIOR-SPEC §3 and §4: a grid of wall
segments with interior segments deterministically omitted, joined wherever
endpoints coincide (R3.1.2, R3.3.5). Nothing was taken from another
application ([CLEAN-ROOM-POLICY](CLEAN-ROOM-POLICY.md)).

Two families, and both are needed:

- `flat-*` and `house-*` are **one join-connected component per level**. Every
  partition meets the shell at a shared node, so R5.1.9's recomputation
  closure is the whole level — legitimately, because there is nothing smaller
  to confine an edit to.
- `wings-*`, `campus-*`, `islands` and the `shape-*` fixtures are
  **multi-cluster**, and are the only shapes on which locality can be a strict
  subset.

Measuring only the first family would report that locality is vacuous;
measuring only the second would report a plan shape few users draw.

## Invalidation locality (R3.4.8, R5.1.9)

`closure` is what the specification PERMITS an edit to recompute. `engine` is what the derived-geometry entry point actually recomputes. `whole level` marks a row where the closure covers the level anyway, so confinement is trivially satisfied and demonstrates nothing.

| Corpus | Class | Components | Closure | Walls | Closure | Faces | Closure | Engine walls | Engine faces | Confined | Whole level |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---|---|

## Thresholds

Issue 0032 requires measured thresholds recorded as acceptance criteria with
explicit failure thresholds. These are they.

### Latency

| Criterion | Value | Where it comes from |
|---|---|---|
| **Acceptance** | p99 gesture latency ≤ **8 ms** at every corpus scale | Half of one 60 Hz frame (16.7 ms), leaving the other half to render. The render budget is issue 0033's to set; this is the core's share of it. |
| **Regression tripwire** | p99 above **1.5×** the value recorded in the table above for that corpus and class | The worst p50 spread across three runs was 17.2%, so 1.5× cannot fire on run-to-run noise. |

The largest corpus, `campus-xl` (330 walls on the measured level, 84 faces),
sits at 4.00–4.41 ms p99 per gesture — inside the 8 ms budget with about 1.8×
headroom. **Nothing in the corpus currently fails the acceptance criterion**,
and the corpus scale at which it would is roughly twice `campus-xl`.

### Memory and allocations

| Criterion | Value | Where it comes from |
|---|---|---|
| **Acceptance** | peak ≤ **4 MiB** above resident, per gesture, at every scale | Measured maximum is 2.2 MiB (`campus-xl`, `wall-create-free`). |
| **Regression tripwire** | ANY change in the allocation count for a class | Allocation counts were byte-identical across all three runs. They are deterministic, so a change is a change in behaviour and has to be explained, not tolerated. |

### What is NOT gated in CI

`scripts/verify.sh` runs the harness in `--smoke` mode and runs the locality
checks; it does **not** compare timings against these thresholds. It cannot
honestly do so: the thresholds are calibrated to the reference host above, and
CI does not run there. Gating them needs a pinned reference runner, which is
owed and recorded against issue 0032. Until it exists, a regression is caught
by running the harness on the reference host and comparing with this table.

## Findings

### 1. The gesture is free; the rebuild is everything

On `wings-l`, fourteen of the fifteen classes cost 1.62–1.68 ms p50 — a
spread of under 4% between creating a wall, dragging a joint, adding a door
and *being refused*. (`wall-delete` is the fifteenth at 1.79 ms; it moves in
the run-to-run noise and is not consistently the slowest.) The whole-level derived rebuild alone costs 1.53 ms.
Committing the batch is under 10% of what a user waits for; the rest is
geometry that mostly did not change. The same pattern holds at every scale:
on `campus-xl` all fifteen classes fall within 3.70–3.76 ms p50 — a spread of
1.6% — against a 2.57 ms rebuild.

This is the single most useful number the corpus produces, and it says where
optimisation effort belongs.

### 2. Recomputation is not confined to the permitted closure

BEHAVIOR-SPEC R3.4.8 confines recomputation after an accepted batch to the
join-connected components of the touched walls plus the R5.1.9 transitive
closure. There is exactly one derived-geometry entry point,
`walls::plan`, and it takes a whole level and returns a whole level.

On the single-component corpora that is legitimate: the closure IS the level.
On the multi-cluster corpora it is a measured violation:

| Corpus | Gesture | Closure permits | Engine recomputes |
|---|---|---|---|
| `wings-l` | `body-drag` | 24 of 211 walls, 5 of 60 faces | all 211 walls, all 60 faces |
| `campus-xl` | `joint-drag` | 54 of 329 walls, 13 of 84 faces | all 329 walls, all 84 faces |
| `campus-xl` | `wall-create-free` | 1 of 330 walls, **0** of 84 faces | all 330 walls, all 84 faces |

The last row is the clearest: drawing a wall in empty space, touching nothing
and enclosing no face, rebuilds every room on the level.

The scoped recomputation that closes this is an acceptance criterion of
**issue 0013** ("common local edits avoid whole-document rebuilds"), not of
this issue; 0032 owns the measurement. `tests/locality.rs` carries a CANARY
that asserts the violation still exists and is designed to FAIL the day it is
fixed, so the gap cannot quietly become a stale claim in this document.

### 3. Locality is vacuous on a normally drawn floor plan

Worth stating plainly because it is easy to assume otherwise: on `flat-s`,
`flat-m` and `house-l` — ordinary plans where every partition meets the shell —
the level is ONE join-connected component and R5.1.9 permits recomputing all
of it. Locality is a real constraint only on levels holding several
disconnected clusters: separate wings, a plan part-way through being drawn,
islands in a courtyard. A scoped engine will therefore help those cases and
will not, by itself, help a single-component flat. Making a single-component
level cheaper is a different problem — incremental union along the touched
boundary — and is not what R5.1.9 asks for.

### 4. Room detection is nearly free once the region is computed

`region` and `plan` differ by less than the run-to-run spread at every scale,
because the faces are traced off the same boundary the region is. Room
detection is not a cost centre; the union underneath it is.

## Coverage gaps

Recorded rather than glossed, because a corpus that hides what it does not
cover is worse than a smaller one that says so.

- **Room record churn is not representable.** Issue 0032's scope names room
  record create/update/delete including cross-level `levelId` moves
  (BEHAVIOR-SPEC §5.2). Rooms are derived geometry with no persisted record in
  this implementation, so there is no entity to churn. The workload becomes
  measurable when §5.2 records exist.
- **`endpoint-drag` has no target on a fully joined plan.** `flat-s`,
  `flat-m`, `house-l` and `islands` have no wall endpoint outside a join, so
  the class is omitted there and exercised on the multi-cluster corpora. The
  harness reports every omission by name rather than shortening its table
  silently.
- **Split remap and straddle rejection (R4.3.3) are not exercised**, because
  they are not implemented: `add_wall_operations` refuses outright to split a
  wall that hosts an opening. The corpus contains the shape; the behaviour to
  measure does not exist yet.
- **Five classes are harness-built** (`detach`, `opening-create`,
  `opening-edit`, `opening-delete`, `host-reverse`): no CLI command produces
  those batches, so the measurement is of the core executing a batch a GUI
  would send, not of a shipped command. The tables mark them `harness`.
  `host-reverse` is the one to watch — R4.3.1's field map is applied by the
  harness because nothing else applies it.
- **Multi-level cost is not aggregated.** Every table measures the FIRST level
  of each corpus. Levels never interact (R5.1.1), so per-level cost composes,
  but a document-wide figure is not published.
- **No reference-host CI runner**, so the thresholds above are not enforced
  automatically. See "What is NOT gated in CI".
